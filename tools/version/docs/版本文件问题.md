# 版本文件问题

## 问题背景

不同项目的版本号并不一定都写在 `package.json` 的 `version` 字段里, 常见情况包括:

- Node 项目写在 `package.json`
- Python 项目写在 `pyproject.toml` 或 `__init__.py`
- Java 项目写在 `pom.xml`
- Docker 镜像版本写在 `Dockerfile` 或 `.env`
- 前端构建注入版本写在 `src/version.ts`
- 单仓库项目可能需要同时更新多个文件

当前 `tools/version` 的能力更偏向:

- `getter`: 负责生成下一个版本值
- `store`: 负责把版本值写进某个文件

现在已经明确需要把 `store` 扩展成对称接口:

- `store.get()`: 读取当前文件中的版本值
- `store.set(value)`: 写入指定版本值
- `store.update(value)`: 以更新语义写入版本值

现在最大的限制是 `store.update(value)` 过于抽象, 只能表达"把值写进去", 但不能很好表达:

- 版本在哪个文件
- 版本在文件里的哪个位置
- 这个文件是什么格式
- 更新时是否需要保留原格式
- 一个版本是否需要同步写入多个文件

所以"版本文件问题"本质不是"怎么生成版本号", 而是"怎么定位并更新不同项目里的版本声明"。

## 目标

这个模块后续最好满足下面几个目标:

- 让调用方声明"版本写到哪里", 而不是把规则写死在代码里
- 尽量复用成熟解析库, 不自己手搓各种文件格式解析
- 支持单文件更新, 也支持多文件联动更新
- 支持不同文件格式, 但统一对外使用一套配置
- 更新失败时能明确知道是"文件不存在"、"路径不存在"、"格式不支持"还是"写回失败"

## 推荐思路

推荐把"版本写入"拆成三层, 不要只保留一个宽泛的 `Store`。

另外, 仓库里已经有 [config-loader](file:///d:/workcode-my/project-base/packages/config/config-loader) 这套通用配置加载能力, 对于 `json/yaml/toml/xml/env` 这类结构化文件, 优先应该复用它, 不要在 `tools/version` 里重复实现一遍解析和序列化。

### 第一层: Target

先描述"版本要更新到哪里"。

这里不要直接让调用方传一个 `Store` 实例, 而是先传一个目标配置:

```ts
export interface VersionTarget {
  type: 'json' | 'text' | 'toml' | 'yaml' | 'xml' | 'env' | 'custom';
  file: string;
  path?: string;
  encoding?: BufferEncoding;
  createIfNotExists?: boolean;
}
```

含义:

- `type`: 文件格式
- `file`: 文件路径
- `path`: 文件内部路径, 例如 `version`、`project.version`、`tool.poetry.version`
- `encoding`: 文件编码
- `createIfNotExists`: 文件不存在时是否允许创建

这一步只负责描述目标, 不负责实现写入逻辑。

### 第二层: Resolver

`Resolver` 负责根据 `VersionTarget.type` 选择合适的适配器。

例如:

- `json` -> `JsonVersionStore`
- `text` -> `TextVersionStore`
- `toml` -> `TomlVersionStore`
- `yaml` -> `YamlVersionStore`
- `xml` -> `XmlVersionStore`
- `env` -> `EnvVersionStore`
- `custom` -> 用户自定义实现

这样以后扩展新格式时, 不需要改 `VersionManager`, 只需要新增一个适配器。

### 第三层: Store Adapter

每种文件格式对应一个真正的写入适配器。

建议把 `Store` 接口从现在只关注 `update()` 的形态, 升级成 `get/set/update` 对称接口:

```ts
export interface Store {
  update(value: string | number): Promise<boolean> | boolean;
}
```

升级为:

```ts
export interface StoreUpdateContext {
  value: string | number;
  file: string;
  path?: string;
}

export interface StoreUpdateResult {
  success: boolean;
  file: string;
  message?: string;
}

export interface Store {
  get(): Promise<StoreGetResult> | StoreGetResult;
  set(value: string | number): Promise<StoreSetResult> | StoreSetResult;
  update(value: string | number): Promise<StoreSetResult> | StoreSetResult;
}
```

这样做的好处:

- `store` 不再依赖构造函数里写死的文件信息
- 返回值可以带错误信息, 便于 CLI 直接展示
- 后续可以扩展 `oldValue`、`newValue`、`changed` 等字段
- 读取和写入共用同一份 target 配置, API 更对称

## 文件格式的处理策略

### 1. JSON

适用于:

- `package.json`
- `manifest.json`
- 各类配置文件

推荐做法:

- 直接复用 `@tikkhun/config-loader` 做加载和保存
- 再配一个对象路径库, 例如 `lodash.get` + `lodash.set`

示意:

```ts
// path = "version"
// path = "build.app.version"
```

优点:

- 实现简单
- 风险最低

### 2. Text

适用于:

- `version.txt`
- `src/version.ts`
- `VERSION`

Text 不应该只有"整文件覆盖"这一种能力, 建议拆成两类:

- `raw`: 直接整文件写入
- `replace`: 按正则替换指定片段

例如:

```ts
export interface TextVersionTarget extends VersionTarget {
  type: 'text';
  mode: 'raw' | 'replace';
  pattern?: string;
  replacement?: string;
}
```

典型例子:

- 把 `VERSION` 文件直接写成 `2026.04.13`
- 把 `export const version = '1.0.0'` 替换成新版本

这个能力非常关键, 因为很多项目虽然不是结构化配置文件, 但本质上只是替换一段字符串。

### 3. TOML

适用于:

- `pyproject.toml`
- `Cargo.toml`

推荐直接用成熟库解析和序列化, 不要自己正则硬改。

原因:

- TOML 层级和数组语法不适合手写替换
- 正则替换很容易误伤注释或相近字段

### 4. YAML

适用于:

- `pnpm-workspace.yaml`
- `docker-compose.yaml`
- 各类 CI 配置

推荐直接使用成熟 YAML 库。

需要接受一个现实:

- YAML 写回后, 注释和格式可能无法完全保留

所以对于 YAML 应该分场景:

- 配置文件允许格式变化: 用 AST/对象写回
- 必须保留格式: 走 `text.replace`

### 5. XML

适用于:

- `pom.xml`

XML 同样建议调成熟库处理, 不建议正则替换整段标签。

因为 XML 常见问题有:

- 命名空间
- 缩进
- 同名节点
- 父子层级定位

### 6. ENV

适用于:

- `.env`
- `.env.production`

这类文件推荐做成单独适配器, 本质是 `key=value` 替换:

- `APP_VERSION=1.0.0`
- `IMAGE_TAG=20260413`

这个场景非常常见, 优先级应该高。

如果已经接入 `config-loader`, `env` 可以直接走结构化 store, 只需要在版本模块里补路径读写和结果包装即可。

## 当前推荐实现

结合现有代码和仓库能力, 推荐当前落地方式如下:

- `ConfigStore`: 负责 `json/yaml/toml/xml/env`
- `TextStore`: 负责 `text.raw` 和 `text.replace`
- `StoreFactory`: 负责把 `VersionTarget` 转成具体 store
- `VersionManager.read()`: 批量读取目标文件中的当前版本
- `VersionManager.set(value)`: 批量写入指定版本
- `VersionManager.update()`: 使用 getter 生成新版本后统一写入

这样实现有两个直接好处:

- `config-loader` 已经解决了大部分配置文件格式问题
- `version` 只需要聚焦"版本字段定位"和"更新结果表达"

## 建议的统一配置结构

建议对外暴露统一配置, 让 CLI 和代码调用都基于同一份声明。

例如:

```ts
export interface VersionManagerOptions {
  getter: Getter;
  targets: VersionTarget[];
}
```

示例:

```ts
const manager = new VersionManager({
  getter: new SemanticVersionGetter({
    file: 'package.json',
    key: 'version',
  }),
  targets: [
    {
      type: 'json',
      file: 'package.json',
      path: 'version',
    },
    {
      type: 'toml',
      file: 'pyproject.toml',
      path: 'tool.poetry.version',
    },
    {
      type: 'text',
      file: 'src/version.ts',
      mode: 'replace',
      pattern: "version\\s*=\\s*['\\\"](?<version>[^'\\\"]+)['\\\"]",
      replacement: "version = '{{version}}'",
    },
  ],
});
```

这个结构的核心价值是:

- 生成版本值的逻辑独立
- 写入目标的逻辑独立
- 一个命令可以同时更新多个文件

## 同文件多目标问题

有一类真实场景需要单独强调:

- 同一个文件里存在多个版本位点

例如 WordPress 插件主文件可能同时包含:

- 文件头部 `Version: 1.2.3`
- 常量 `define('WLD_VERSION', '1.2.3')`

如果多个 `target` 命中同一个文件, 并且执行层采用并发写入, 就会出现后写入覆盖前写入的问题。

所以实现上必须满足:

- `read` 可以并发, 但 `set/update` 更推荐顺序执行
- 至少要保证同一文件内的多个 target 按声明顺序串行写入

当前更稳的做法是:

- `VersionManager.set()`
- `VersionManager.update()`

都按 target 顺序逐个执行, 这样可以天然支持"同一文件多处替换"。

## 配置文件驱动

对于业务项目, 更推荐最终形态是:

- 项目里提供一份 `version.json`
- CLI 直接读取 `version.json`
- `version.json` 只描述 getter 和 targets
- 业务侧不再自己写 `upgrade-version.js`

示意:

```json
{
  "getter": {
    "type": "semantic",
    "file": "./package.json",
    "key": "version",
    "position": "patch"
  },
  "currentTargetIndex": 0,
  "targets": [
    {
      "type": "json",
      "file": "./package.json",
      "path": "version"
    },
    {
      "type": "text",
      "file": "./wp-link-dispatcher.php",
      "mode": "replace",
      "pattern": "Version:\\s*(\\d+\\.\\d+\\.\\d+)",
      "replacement": "Version: {{version}}"
    }
  ]
}
```

这样 CLI 就可以直接工作:

```powershell
semantic-version read --config version.json --value-only
semantic-version update --config version.json --position patch
```

这个模式的价值是:

- 版本规则变成声明式配置
- 项目迁移时只需要复制 `version.json`
- 不同项目可以共享同一个 CLI, 不需要重复写脚本

## 推荐的内置适配器优先级

第一阶段建议只做最有价值的几种:

1. `json`
2. `text.raw`
3. `text.replace`
4. `env`

第二阶段再补:

1. `toml`
2. `yaml`
3. `xml`

原因很简单:

- `json` 和 `text` 已经覆盖大量 Node 和前端项目
- `env` 可以覆盖构建注入和镜像标签场景
- `toml/yaml/xml` 虽然重要, 但实现和兼容成本更高

## 自定义扩展机制

除了内置适配器, 最好允许业务方自定义写入逻辑。

例如:

```ts
export interface CustomStore extends Store {
  support(target: VersionTarget): boolean;
}
```

或者更直接一点:

```ts
export interface VersionTarget {
  type: 'json' | 'text' | 'toml' | 'yaml' | 'xml' | 'env' | 'custom';
  file: string;
  path?: string;
  update?: (value: string | number) => Promise<void> | void;
}
```

适用场景:

- 版本不是写文件, 而是调用外部命令
- 版本需要同步写数据库
- 版本要经过特殊格式转换

这样 `tools/version-plugins` 也能自然接入, 不会被核心包写死。

## 和当前结构的兼容建议

当前代码已经有:

- `Getter`
- `VersionManager`
- `Store`

所以不建议推翻重写, 建议平滑演进:

### 方案 A: 最小改造

保留 `Store`, 但新增更多 `Store` 实现:

- `JsonStore`
- `TextReplaceStore`
- `EnvStore`
- `TomlStore`

优点:

- 改动最小
- 可以快速上线

缺点:

- `store` 的构造参数会越来越重
- 多文件更新和统一配置不够优雅

### 方案 B: 推荐方案

引入 `targets` + `storeFactory`:

- `VersionManager` 只负责拿到新版本
- `storeFactory` 负责把 `target` 转成 `store`
- `store` 负责执行更新

优点:

- 架构清晰
- 扩展性更强
- 更适合做 CLI 和插件体系

缺点:

- 需要补一层适配器工厂

如果只看长期维护成本, 更推荐方案 B。

## 错误处理建议

版本更新属于自动化流程的一部分, 错误信息必须能直接定位问题。

建议不要只返回 `boolean`, 而是返回结构化结果:

```ts
export interface VersionUpdateResultItem {
  file: string;
  success: boolean;
  oldValue?: string | number;
  newValue?: string | number;
  message?: string;
}
```

CLI 输出时就可以直接展示:

- 哪个文件更新成功
- 哪个文件没找到
- 哪个路径不存在
- 哪个替换规则没有命中

## 最终建议

一句话总结:

> 把"版本文件问题"定义成"版本目标定位 + 文件格式适配 + 多目标批量更新"问题, 而不是只做一个简单的 `package.json version` 写入器。

推荐落地顺序:

1. 先把 `Store` 的返回值升级为结构化结果
2. 增加 `text.replace` 和 `env` 两种高频能力
3. 引入统一 `VersionTarget` 配置
4. 再逐步补 `toml/yaml/xml` 适配器
5. 最后把 `tools/version-plugins` 接成自定义扩展入口

这样做的好处是:

- 现有代码可以继续用
- 近期可以快速解决大多数项目的版本落盘问题
- 后续扩展到 Python、Java、Docker、Monorepo 也不会重构一次架构
